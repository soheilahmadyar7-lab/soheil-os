# SOHEIL Security Architecture

Status: **Security baseline established in v0.3.1-security**
Reference baseline: OWASP MASVS (Storage, Crypto, Auth, Network, Platform, Code, Resilience, Privacy)

## 0. Non-negotiable statement

SOHEIL is designed as a private Life Vault. Security is an architectural invariant, not a feature.
No software can be made permanently immune to future vulnerabilities; dependencies, Android, cryptographic guidance and the threat landscape change. Therefore this architecture minimizes the amount of redesign required, while dependency patches, key rotation and vulnerability-response updates remain mandatory security maintenance.

## 1. Threat model

Protect against:
- lost/stolen locked phone;
- casual access to an unlocked phone;
- extraction of app files/backups;
- malicious ordinary Android apps;
- lock-screen/notification leakage;
- screenshot/recents leakage;
- accidental plaintext logging or analytics;
- accidental cleartext networking;
- leaked API keys/signing material in source control;
- tampered local ciphertext;
- future AI over-collection (sending too much context);
- future backend compromise blast radius;
- supply-chain/dependency vulnerabilities.

Cannot guarantee confidentiality on a fully compromised/rooted device while SOHEIL is actively unlocked. Root detection is advisory and bypassable; encryption/authentication remain the primary controls.

## 2. Data classification

- PUBLIC: app UI labels, version, non-sensitive code.
- PRIVATE: tasks, goals, focus, ordinary notes.
- SENSITIVE: journal, emotions, health, relationships, financial context, Jarvis conversation.
- RESTRICTED: recovery material, authentication tokens, sync keys, signing/backend secrets.

Passwords, card PINs and production cryptographic private keys are not normal SOHEIL content. Dedicated password managers/HSM/CI secrets are preferred.

## 3. Key hierarchy

### Device KEK
- Generated by Android Keystore.
- AES-256/GCM.
- Non-exportable key material.
- User authentication required.
- `unlockedDeviceRequired` on supported Android versions.
- StrongBox requested where available; TEE/Keystore fallback otherwise.

### Vault DEK
- Random 256-bit key generated with `SecureRandom`.
- Stored on disk only wrapped by the Keystore KEK using AES-GCM.
- Unwrapped only after BiometricPrompt/device credential authentication.
- Exists in process RAM only during an unlocked SOHEIL session.
- Explicitly zeroized on app lock.

### Record encryption
- AES-256-GCM, 128-bit authentication tag.
- Fresh random 96-bit nonce per encryption.
- Versioned envelope (`S2`) to allow future crypto migrations.
- GCM authentication failure is treated as corruption/tampering and fails closed.

Keys/API secrets must never be hard-coded in APK/source.

## 4. Authentication and session policy

- SOHEIL opens locked.
- Unlock via AndroidX BiometricPrompt.
- Allowed authenticators: BIOMETRIC_STRONG or DEVICE_CREDENTIAL.
- Background auto-lock default: 30 seconds.
- Inactivity auto-lock default: 5 minutes.
- Manual Lock Now is always available.
- Lock closes the DB and zeroizes the Vault DEK.
- A device without secure screen lock must not silently downgrade to an unprotected vault.

Future high-risk actions may require step-up/re-authentication even during an unlocked session.

## 5. Local storage

Sensitive content is encrypted before SQLite/SharedPreferences persistence.
Current encrypted content includes:
- Capture text;
- task title and area;
- Memory text/tags;
- Jarvis conversation text;
- Daily Check-in payload;
- Focus/other sensitive preferences;
- Jarvis access-audit details.

Operational metadata required for functionality (e.g. task due timestamp/status/count) may remain non-secret. Minimize metadata whenever possible.

Legacy plaintext migration:
1. authenticate/unlock Vault;
2. encrypt legacy columns in place;
3. migrate Daily State into encrypted payload table;
4. drop plaintext table;
5. enable SQLite secure_delete;
6. VACUUM after successful migration.

Never store sensitive data in external/public storage.

## 6. Backup and recovery

Automatic Android cloud backup and device-transfer extraction are disabled/excluded for the Vault because device-bound Keystore material is intentionally not portable.

Future cross-device recovery MUST use an explicit encrypted export design:
- user-initiated only;
- independent recovery encryption key derived from a high-entropy passphrase/recovery secret;
- authenticated encryption;
- no plaintext export;
- clear warning that loss of recovery secret can make the backup unrecoverable;
- backup import requires fresh local authentication.

Do not weaken device encryption merely to make backups convenient.

## 7. Screen and UI privacy

- FLAG_SECURE enabled globally.
- Recent-app screenshot disabled when API supports it.
- Autofill disabled for sensitive app views.
- IME personalized-learning disabled for SOHEIL text inputs.
- Lock screen displays no private content.
- Clipboard use for sensitive data should be avoided and time-limited if ever introduced.

## 8. Notifications

Notifications are privacy-preserving by default:
- no task title/journal/health content on lock screen;
- generic private reminder text;
- private notification visibility;
- tapping notification opens locked SOHEIL and requires authentication.

A future user option to show notification content must be explicit opt-in, never default.

## 9. Android permissions

Principle: default deny and least privilege.

Current permission: POST_NOTIFICATIONS only.
No INTERNET, storage, location, contacts, calendar, microphone, camera or health permission exists in the security baseline.

Future permissions must:
1. be directly tied to a user-visible feature;
2. be requested just-in-time;
3. use the narrowest Android permission/API scope;
4. be revocable;
5. be reflected in Jarvis Access;
6. be included in security review/CI permission allowlist.

## 10. Network security

Current app has no INTERNET permission.
Global network policy already forbids cleartext HTTP.
Future network code must:
- use HTTPS only;
- use platform TLS certificate/hostname verification;
- use a centralized network layer;
- implement authentication/token expiry/rotation;
- never disable certificate validation;
- never trust user-added certificates in production unless explicitly required by a documented enterprise mode;
- use endpoint pinning only with a safe rotation/backup-pin strategy where operationally appropriate.

Production endpoint identity and pin configuration cannot be finalized before an endpoint/certificate exists; this is endpoint configuration, not a redesign of the security architecture.

## 11. Jarvis / AI privacy boundary

Local-first by default.
Remote AI access follows **Minimum Necessary Context**:
1. user request enters Context Engine;
2. permission policy selects allowed domains;
3. relevance filter selects only necessary records;
4. sensitive-domain policy may require per-request consent;
5. selected context is logged in an access audit;
6. only then can data be sent over authenticated TLS.

Remote AI must never receive the entire database by default.

Domain model (default remote policy):
- TASKS: deny until user enables remote Jarvis;
- INBOX: deny until enabled;
- MEMORY: deny / ask every time for sensitive classes;
- JOURNAL: deny / explicit consent;
- HEALTH: deny / explicit consent;
- FINANCIAL: deny / explicit consent;
- CONTACTS/PEOPLE: deny / explicit consent;
- CALENDAR: deny until enabled;
- LOCATION: deny unless needed for the active request;
- FILES: deny unless explicitly selected.

Future `Jarvis Access` UI must show domain permissions and recent access.

## 12. Cloud sync architecture

If sync is added, sync and AI processing are separate concepts.
Preferred sync model: client-side encrypted blobs; server does not need plaintext for ordinary storage/sync.
- per-user/device authenticated sessions;
- short-lived access tokens;
- refresh-token protection;
- device revocation;
- server-side rate limiting;
- encryption in transit and at rest;
- audit logs;
- deletion/retention controls;
- recovery design independent from AI provider credentials.

## 13. Backend and API secrets

Never ship provider/API secrets in the APK.
Android -> SOHEIL backend -> external AI/provider.
Production backend secrets belong in a managed secret store/CI environment, not Git.
Backend must not log raw Life Vault context by default.
Use structured allowlisted logging with sensitive-field redaction.

## 14. Release signing and build integrity

- Debug/test signing is not production trust.
- Production APK must use a dedicated SOHEIL signing key.
- Signing private key must live in CI secret storage/HSM-equivalent, never repository/history.
- Release build: debuggable=false, R8/minification/shrinking enabled.
- CI must verify APK signature/certificate before publishing.
- Signing key must have a documented offline recovery/escrow process controlled by the owner.

No safe production signing key can be auto-created and committed to a public repository. Secret provisioning is an operational ceremony, not application code.

## 15. Supply chain and CI

- Dependabot for Gradle/GitHub Actions.
- CodeQL/static analysis.
- Security invariant gate.
- no unreviewed binary dependencies;
- prefer stable AndroidX releases;
- pin/upgrade dependencies intentionally;
- dependency vulnerabilities are patched as security maintenance.

## 16. Logging, analytics and crash reporting

Default: no third-party analytics, ads or crash reporter.
Never log:
- captures/journal/memories;
- health/relationship/financial content;
- authentication tokens;
- encryption material;
- remote AI prompts/context.

If telemetry is introduced, it must be opt-in or strictly privacy-preserving and schema-allowlisted.

## 17. Integrity / compromised-device policy

Local root/test-key indicators are advisory only.
Future connected versions should use Android/Google Play integrity attestation where deployment environment permits, verified server-side.
Integrity failure should reduce high-risk remote capabilities rather than pretending client-side root detection is an unbreakable security boundary.

## 18. Data deletion

- Delete records from the database through the Vault layer.
- Encryption means deleted ciphertext does not reveal plaintext.
- SQLite secure_delete is enabled.
- Full account/device decommission should delete wrapped keys first (cryptographic erasure) and then local files.
- Remote deletion must propagate to sync/backend according to retention policy.

## 19. Patient/regulated data boundary

SOHEIL is not a clinical EMR/EHR by default. Do not store identifiable patient records until the deployment has a separate regulatory/compliance architecture (jurisdiction, access control, auditability, retention, breach response, BAAs/contracts where applicable).

## 20. Security update policy

Security architecture should remain stable, but **security updates can never be promised away**. Required ongoing work includes:
- Android/API behavior changes;
- dependency CVEs;
- cryptographic deprecations;
- backend vulnerabilities;
- signing/token/key rotation;
- newly discovered attack techniques;
- changes to OWASP MASVS/MASTG guidance.

A future SOHEIL version is not allowed to weaken these invariants silently. Any intentional exception requires a documented security decision and user-visible impact assessment.
